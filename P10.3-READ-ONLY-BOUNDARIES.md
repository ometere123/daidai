# P10.3: server-owned, read-only boundaries for authoritative invoice data

P10.3 builds on the P10.2 internal projection, merged into `main` at `dabc3250c022be7bbe6289c081c695b78ba2ab76`. It adds four read-only integration boundaries:

- durable attempt lineage;
- trusted evidence adapters;
- invoice-scoped viewer access;
- historical authorization semantics.

**Nothing in this phase is wired to a route.** It adds no wallet calls, signatures, approvals, swaps, payouts or registration actions.

## Trust boundaries

```
client ──(opaque credential)──▶ ViewerAuthenticator ──▶ AuthenticatedViewer (in-process brand)
                                                          │
                       PermissionStore (tenant directory + explicit invoice:read) ──▶ ViewerGrant
                                                          │   (no grant ⇒ no reads at all)
                                                          ▼
 readAuthoritativeInvoice ◀── invoiceSnapshotReader     (read-only SQLite, re-derived commitment)
                          ◀── authorizationObserver     (EIP-712 signer recovery; time-independent)
                          ◀── AttemptLineageReader      (read-only SQLite)
                          ◀── transactionVerifier       (readOnlyRpc: 4 read methods only)
                          ◀── canonicalBlockReader      (readOnlyRpc)
```

- **Attestation, not labels.** `src/evidence-attestation.ts` keeps an in-process brand (a WeakSet). The adapters add it only after their own verification, and the projector requires it on every record. A record with the right `source` label but without the brand never establishes authority. That covers plain objects, JSON round trips and client-supplied data.
- **Read-only by construction.**
  - SQLite readers open with `readOnly: true` and `PRAGMA query_only`.
  - Chain access is wrapped in `readOnlyRpc`, which refuses everything except `eth_chainId`, `eth_getTransactionByHash`, `eth_getTransactionReceipt` and `eth_getBlockByNumber`. That includes `eth_sendRawTransaction`, every signing method and every `wallet_*` method.
  - Authorization adapters only recover signers from stored signatures; they never request one.
- **Viewer access comes first.**
  - `src/viewer-access.ts` mints an `AuthenticatedViewer` only from a server `ViewerAuthenticator`.
  - The `authorize` port then requires three things: the server tenant directory says the invoice belongs to the viewer's tenant, an explicit `invoice:read` permission exists, and the session hasn't expired.
  - Client-built viewer objects or grants, wallet connections, invoice approvals and recipient consents are not viewer authentication.
  - Unauthorized and cross-tenant requests are rejected before any invoice data is read; tests check this.

## Durable attempt lineage (`src/attempt-lineage.ts`)

- **What each attempt records:** tenant, invoice, commitment digest, **the invoice revision current when it was claimed**, operation (`conversion` or `payout`), a unique attempt ID, the authorization fingerprint it was claimed under (digest, both signers, expiry), the transaction envelope it may send (chain, to, SHA-256 of the calldata, value), and its dispatch/hash state. Verification and reconciliation results are appended to an event history.
- **Rules enforced by SQLite itself:**
  - Identity columns are immutable.
  - Attempts can't be deleted.
  - A hash is set once and is unique across attempts.
  - Closure is final.
  - Events are append-only.
  - Only one open attempt may exist per (tenant, invoice, digest, operation). A second attempt requires an explicit `close(..., 'reconciled-not-landed', ..., operator)` by a named operator. Nothing retries automatically.
- **Mixed revisions:** the invoice revision can move on, and each attempt keeps the revision it was recorded at. Transaction evidence must carry the attempt's own recorded revision, so evidence relabelled with the newest revision is rejected. An attempt that claims a revision newer than the committed invoice is a mismatch.
- **Legacy data:** the existing `Spike` harness records `swapId`/`payoutId` but not the revision, authorization or hash at claim time. `importLegacy` keeps these attempts as `lineage: 'unresolved'` with no revision. The projector reports them as `reconciliation-required / lineage-unresolved`, and they block a fresh attempt until a human reconciles them. Nothing is guessed.
- **Ambiguity fails closed:**
  - Two open attempts for one operation give `multiple-attempts`.
  - A claimed attempt with no hash (a crash, or a wallet error after submission) gives `unknown / missing-hash`.
  - Attempts from another tenant or commitment give `mismatch`.

## Trusted evidence adapters (`src/evidence-adapters.ts`)

| Adapter | Verifies before attesting |
| --- | --- |
| `invoiceSnapshotReader` | Server tenant ownership, then re-derives the commitment digest from the stored invoice and compares the revision |
| `authorizationObserver` | Recovers the EIP-712 signer for the requested purpose (domain "Daidai invoice authorization", the committed digest, the expected audience) and requires the invoice's approver or recipient |
| `transactionVerifier` | Chain 42220, sender is the taker, `to`/calldata digest/value equal the attempt's recorded envelope, Daidai attribution suffix, receipt success, log integrity (same tx and block, no removed or duplicate logs), exact cNGN output, USDt debit within the cap for a conversion and zero for a payout, no unexpected transfers. Bound to the attempt ID and recorded revision |
| `canonicalBlockReader` | Canonical block hash and timestamp at the height, and the finalized head |

The projector then cross-checks:
- the transaction block against the canonical hash;
- finality, by comparing the finalized head with the transaction block;
- that both observations are fresh;
- that the conversion and payout are distinct and correctly ordered.

## Historical authorization semantics

| State | Meaning |
| --- | --- |
| `verified` | Signature verified, bound to the commitment and audience, and currently unexpired |
| `verified-at-execution` | Signature verified and now expired, but both operations are independently finalized and their **canonical block timestamps** are before expiry. Each attempt must have been claimed under this exact authorization fingerprint, before expiry. `executedAtMs` reports the later execution time |
| `stale` | Expired without that proof, or the observation is too old |
| `unverified` | Missing, or doesn't match the signer, purpose, audience, commitment or an attempt's recorded fingerprint |

A finalized historical payment is no longer reinterpreted just because its authorization later expired. Expiry does not make it unauthorized after the fact. The other settlement checks (exact output, debit cap, finality, attempt binding, distinct operations) are unchanged, and the wire validator recomputes `executedAtMs` from the operations. A payment that executed at or after expiry stays `stale` and cannot settle.

Authorization is now bound to (tenant, invoice, commitment digest) rather than also to the storage revision. The EIP-712 signature commits to the digest, and requiring the current storage revision made a valid signature fail as soon as the record advanced. Transaction evidence is still bound to the attempt's recorded revision.

## Wire schema v2 (internal only)

- `schemaVersion: 2`.
- Operations add `recordedRevision`, plus the reasons `lineage-unresolved` and `multiple-attempts`.
- Transaction evidence adds `blockTimestampMs`.
- Authorization adds the `verified-at-execution` state and `executedAtMs`.
- The internal `AuthoritativeInvoiceView` displays these fields. It still has no route.

## Adversarial review

The independent agent wrote 85 attacks in `test/p103-adversarial.test.ts`. They cover forged and serialized evidence, Proxy and getter tricks, amount, chain, tenant and attempt mismatches, historical-authorization edge cases, direct SQLite tampering, viewer forgery, and an RPC guard plus adapter rejection matrix. On the first run, 80 passed and 5 exposed real defects. All five are fixed in source and kept as regression tests named `FIXED (adversarial finding): …`.

| # | Finding | Severity | Fix |
| --- | --- | --- | --- |
| 1 | `INSERT OR REPLACE` could rewrite an attempt's identity and hash. REPLACE's implicit delete fires neither the update nor the delete triggers | High (lineage integrity) | A `BEFORE INSERT` guard on an existing `attempt_id` |
| 2 | The same REPLACE could overwrite append-only events | High | A `BEFORE INSERT` guard on an existing `seq` |
| 3 | The viewer authorizer granted access to an expired viewer if the clock returned NaN | Low | The clock value is validated, and the comparison is written as `now < expiresAtMs` |
| 4 | `authenticateViewer` re-read authenticator fields after validating them, so a getter could swap them | Low | Fields are read once, then validated and frozen |
| 5 | The duplicate-log check compared raw `logIndex` strings, so `0x1` and `0x01` counted twice | Low to medium (needs a lying RPC) | Strict quantity parsing and numeric deduplication |

Also hardened: a closed attempt's `hash` and `dispatch` are now frozen by a trigger. The agent noted this gap but did not count it as a finding.

What the agent could not test:
- **Chain behaviour:** live reorgs between block reads, and whether the block at a height is an ancestor of the finalized head. Both need a real chain.
- **Write concurrency:** truly parallel writers. `node:sqlite` is synchronous, so two handles were used one after the other.
- **Production identity and stores:** a real identity provider and a production signature store don't exist yet.

## Unresolved blockers before any route

1. **Viewer authentication:** there is no real authentication or session provider. `ViewerAuthenticator` and `PermissionStore` are interfaces exercised with controlled test identities.
2. **Production storage:** there is no production invoice, signature or attempt store. The adapters read the `Spike` harness schema and the new lineage database. The execution path (`Spike.claimSwap`/`claimTransfer`) does not yet write lineage records at claim time. That wiring belongs to the execution service and needs its own review.
3. **Chain reader:** there is no reviewed production chain reader for these adapters. Tests use a deterministic in-memory chain behind `readOnlyRpc`. The private RPC configuration was not touched.
4. **Finality policy:** finality uses the RPC's `finalized` block tag. The product decision on how many confirmations count as final is still open.
5. **Attribution code:** it is injected; a production value must come from server configuration.
6. **Attestation scope:** the brand is in-process. A multi-process deployment would need signed attestations or a single trusted projector process.
