## Architecture decisions

| # | Requirement | Decision | Why / approval needed |
| --- | --- | --- | --- |
| 1 | Real viewer authentication with a session lifecycle | Server-owned sessions in D1, issued by exchanging a **single-use, short-lived invitation** created by an operator CLI. Sessions have an opaque 256-bit token (stored as SHA-256), a 12 h absolute lifetime, a 30 min idle timeout, rotation on exchange, explicit revocation (logout and an operator revoke), and a per-session record of tenant and viewer. The Vercel server holds the token only in a `__Host-` cookie (HttpOnly, Secure, SameSite=Strict, Path=/) and never exposes it to client JavaScript | There's no identity provider today. An `IdentityProvider` boundary (OIDC/passkeys) is defined so a real provider can replace invitations; choosing and configuring one needs owner approval. The P10.4 environment-variable demo token is **removed** from the authenticated flow |
| 2 | No public preview exposure | Every private page needs a valid session. In addition, private routes return 404 on Vercel **Preview** unless the server variable `DAIDAI_PREVIEW_ACCESS=1` is set **and** a session exists, and on Production unless `DAIDAI_APP_ENABLED=1`. Pages send `noindex` and `no-store` | An environment flag alone never exposes data: a session is always required, and sessions come only from invitations |
| 3 | Global replay protection | A D1 `service_nonces` table with primary key `(key_id, nonce)`. A request claims its nonce with one `INSERT` *after* its signature verifies. A duplicate fails on D1's single primary, so it's consistent across isolates. Old rows are pruned outside the ±60 s window. The per-isolate window remains as a fast path | Tested across **two separate Worker instances** sharing one persisted D1 |
| 4 | Read-only Celo chain reader | `src/celo-rpc.ts`: a JSON-RPC-over-fetch transport behind P10.3's `readOnlyRpc` (4 read methods, with timeouts and size limits), wired into `chain-evidence.ts` adapters. Covers canonical block hash, `finalized` tag, reorg detection by re-reading block hashes, transaction identity, exact cNGN output and the USDt max debit. Configured only by the Worker variable `DAIDAI_CHAIN_RPC_URL` (unset by default) | Tests use a deterministic JSON-RPC server, including reorg, non-final and mismatch cases. An optional manual read-only probe against public Forno is in the docs; CI never uses live RPC. A production endpoint needs owner approval |
| 5 | Claim-time lineage | `src/claim-coordinator.ts`, for an **isolated test environment only**. Steps: preflight → reserve the taker nonce → `recordAttempt` (persisted) → *simulated* dispatch → `recordHash` or `recordOutcomeUnknown`. A `taker_nonces` table (chain, sender, nonce, unique) prevents nonce reuse across invoices. The only dispatcher is `SimulatedDispatcher`, and there is no real dispatcher | Tests cover crashes at each step, concurrent claims, unknown hashes, cross-invoice nonces and duplicate payment |
| 6 | Read-only user flow | `/login` (invitation exchange), `/invoices` (permitted list), `/invoices/[id]` (authoritative view), and `/logout`. Ink and Brass is kept, and the fixture demo at `/` is unchanged. Authoritative evidence is labelled; no synthetic receipt is ever shown as live | Session-gated |
| 7 | Textile requirements | Documented in [Before real Textile FX](#before-real-textile-fx-quote-conversion-and-payout) | Not implemented: needs owner authorization per transaction |

## Trust boundaries (additions to P10.4)

| Boundary | Mechanism | Never trusted |
| --- | --- | --- |
| Browser → Vercel (session) | A `__Host-daidai_session` cookie (HttpOnly, Secure, SameSite=Strict). State-changing route handlers (login, logout) also check `Origin` against the deployment host | Session IDs in URLs; client-readable tokens; cross-site POSTs |
| Vercel → Worker (session ops) | HMAC-signed requests over the body, with the global nonce. `POST /v1/sessions` exchanges an invitation, `DELETE /v1/sessions/current` revokes, `GET /v1/invoices` lists permitted invoices | Unsigned or replayed requests, including across isolates |
| Worker → chain | `readOnlyRpc`, plus timeouts, response size limits and chain-ID checks | Any write or sign method; data from a mismatched chain ID |
| Coordinator → dispatcher | Only `SimulatedDispatcher` exists. Lineage is persisted *before* dispatch | A dispatch without a persisted claim; nonce reuse |

## Failure modes

| Failure | Required behaviour |
| --- | --- |
| Invitation reused, expired, unknown, or for another tenant | A uniform `invalid-credentials`; no session is created; the attempt is rate-limited |
| Session expired (absolute or idle), revoked, or rotated away | `not-found-or-forbidden`, and the Vercel server clears the cookie |
| Nonce replayed on another isolate | 401, because the D1 nonce claim fails |
| D1 nonce store unavailable | Fail closed with 503; never fall back to accepting the request |
| RPC timeout, chain-ID mismatch or oversized response | The operation is `unknown/unavailable`, never verified |
| Reorg (block hash changed) | `reconciliation-required` |
| Crash between claim and dispatch, or after dispatch before the hash | The attempt is retained (`claimed` / `outcome-unknown`), blocks new attempts, and there is no retry |
| Two invoices reserving the same taker nonce | The second is refused |

## Before real Textile FX quote, conversion and payout

Nothing below is implemented as a live path. Each item is a prerequisite, and every real transaction needs separate human authorization.

### A. Identity, authority and approvals
1. **Viewer identity:** a real identity provider (OIDC or passkeys, chosen by the owner) behind the `IdentityProvider` boundary, replacing operator-issued invitations for viewers.
2. **Operator identity:** operator authentication distinct from viewer authentication, with an `execute:conversion` / `execute:payout` permission and two-person approval for amounts above an owner-set threshold.
3. **Per-transaction approval:** every real transaction is approved in MetaMask by the operator, on the Daidai taker EOA, after a review screen showing the exact envelope. No automatic signing.

### B. Quote (Textile RFQ)
4. **Exact-output request:** `exactOutRequest(invoice)` (in `src/textile.ts`) against the live Textile RFQ endpoint, with the official taker proof (`src/taker-proof.ts`, EIP-712 "Textile Taker Control") signed by the operator.
5. **Quote acceptance:** accept a quote only if `parseTextileQuote` succeeds and `Spike.validateQuote` passes (corridor, exact cNGN output, `takerPays` ≤ `maxSell`, fee ≤ debit, approval spender = reactor, amount = debit). Expiry is checked at signing time, not just at receipt.
6. **Endpoint review:** review Textile's live terms, rate limits and error semantics. Network access to Textile needs owner approval.

### C. Preflight (before claiming)
7. **Wallet checks:** `CeloReader.preflight`: EOA only (no delegated code), gas and fee ceilings including the L1 rollup fee, native gas balance, `eth_call` success and an `eth_simulateV1` swap simulation that matches exact output and debit.
8. **Balances:** USDt balance ≥ debit, and an allowance of exactly the debit (or an owner-approved ceiling) to the Textile reactor. The approval is itself a separately authorized transaction.

### D. Claim and dispatch
9. **Claim before dispatch:** a claim-time lineage write through `ClaimCoordinator` semantics (attempt + taker-nonce reservation persisted before dispatch) against the **production lineage store**, which needs an approved migration and a durability review. D1 needs global replay protection (done here) and an access pattern that keeps the read path read-only.
10. **A reviewed real dispatcher:** it hands the exact claimed envelope and the reserved nonce to MetaMask (`eth_sendTransaction` through the existing wallet boundary) and records the hash immediately. It does not exist yet, and the coordinator refuses any non-simulated dispatcher until it is reviewed.

### E. Verification, finality and reconciliation
11. **Production chain reader:** a reviewed read-only endpoint (a provider key as a Worker secret, approved by the owner) wired through `DAIDAI_CHAIN_RPC_URL`. `recordVerifiedFinal` is driven only by attested adapter output.
12. **Finality policy:** a decision is needed. The current implementation uses the RPC `finalized` tag; the owner may require extra confirmations or a second independent reader.
13. **Authoritative reconciliation:** proof of non-execution (nonce consumed by another transaction, or a finalized cancel or replacement) and an authorized reconciler. Until then, an unknown outcome blocks forever, by design.

### F. Payout
14. **Separate payout attempt:** a separate payout attempt (exact `transfer(recipient, buyAmount)` on cNGN, attributed) only after the conversion is `verified-final`, under the same authorization rules. No combined swap-and-pay.

### G. Operations
15. **Funding and limits:** USDt for conversion, CELO for gas, and owner-set per-invoice and daily limits.
16. **Hosting:** Vercel Hobby is non-commercial; real payment volume needs an owner decision on hosting terms.
17. **Monitoring and incidents:** alerts on `outcome-unknown` attempts, reorg mismatches and nonce gaps, and an incident runbook.

### Security review results

- The HMAC now signs the key ID along with the request. The regression uses duplicate material under different IDs to confirm that a signed request cannot change replay namespaces. Separate current and retiring keys are supported only while explicitly configured. Roll the Next.js signer and Worker verifier together when adopting the new wire format.
- Replay insertion requires a successful D1 result with exactly one changed row. A failed write or missing acknowledgement denies the request before private invoice reads. Worker tests also exercise shared persisted replay state with separate isolates and concurrent duplicates.
- A successful invitation exchange creates a fresh session and revokes the previous browser session in one batch. A used or invalid invitation leaves the prior session alone. Logout returns an error when server revocation cannot be confirmed and preserves the browser cookie so the operator can retry logout.
- Negative cases use separate controls at each boundary. Worker authorization tests assert no invoice, signature or attempt query on denial. RPC cases isolate the wrong chain, returned transaction hash, token, recipient, amounts, finality and canonical block from malformed response, request ID, timeout, size and method errors. Lineage tests preserve the original commitment and attempt across revisions and block duplicate claims and ambiguous outcomes. Dispatch in those tests is simulated.
- The full browser flow uses newly seeded local identities and verifies private gates and fixture separation. Its wallet spy counts calls across navigations and tabs. No wallet-provider method was called in that flow. No real wallet, transaction dispatcher or live chain endpoint was used.
