## Work allocation / dependencies
Financial path critical: M0 → M1 → M2 → M3. Public UX and evidence structure, user recruitment and provenance review can progress independently; do not merge a conflicting journal/route design. Developer A: canonical mapper, SQLite, state/verification; B (if available): RFQ/RPC/bridge integration; C: public proof, UI, narrative and user coordination. For solo developer, timebox UI until P0 money gates pass. Use existing tests and source, not duplicate application. Every task references R IDs and TESTING evidence. Do not count sponsor documentation as a passing probe.

## Immediate technical tasks
1. Re-read wallet.ts, settlement-review.ts, attempt-lineage.ts, lineage-schema.ts and product digest implementation. Trace exact state/dispatcher interfaces; choose one authoritative local journal. Preserve historical tests.
2. Read-only endpoint qualification on approved network. Alchemy/QuickNode document Celo eth_simulateV1; Forno previously refused. Capture sanitized response/capability matrix, no credential. Inspect current Textile OpenAPI and preview; check supported corridor/size. Do not weaken exact-transfer simulation or quorum if unavailable.
3. Confirm external supplier actually accepts cNGN, legitimate enrolled-wallet payer owns funds, consent and invoice description. If payer model incompatible, ask organiser about attribution and do not take custody. Confirm wallet code and current registration without replay.
4. Add incremental journal/restart regressions before enabling live dispatch. Enforce same invoice ID across revisions; unknown claims block. Reconcile persisted exact envelope and rederive verified proof, not WeakSet serialization.
5. Build controlled real adapter with explicit mode, allowlisted wallet review, atomic claim, strict preflight. Public profile remains no financial mutation. Do not use legacy Spike/MockChain as second writer.
6. Run first safe pilot, collect evidence, then polish. No artificial activity or claim of guaranteed payment.

## Fallback and stop conditions
If RPC method unavailable, try another approved documented provider; if no qualified provider, stop live dispatch and submit only honest control-plane demo if appropriate (not eligible for Textile until live criteria met). If venue has no quote, wait/refresh only before claim, release unused reservation as supported; no unsupported routes. If real user unavailable, do not fake one. If hosted product blocked, retain public static/read-only proof plus local controlled pilot, clearly distinguish them. Cut P1/P2 first; do not cut authorisation, durable claims, finality, safe resumption, real payout or attribution. If deadline cannot be met, disclose missing gate. No second track or rebuild.

## Hosted application roadmap (PDR-002)
The financial path in qualification mode (M0 to M3) and the hosted path below run in parallel and meet at the first real transaction. Hosted routes open only through the gates in TESTING. Dates are targets, not guarantees, and every external dependency is named.

| Step | Deliverable and exit gate | Depends on | External dependency |
|---|---|---|---|
| H1 wallet authentication | Server-composed, audience-bound, single-use, five-minute EIP-712 sign-in verified in the Worker; session identity is the wallet address; invitations kept for demonstrations; login page connects the wallet with real account access. Gate: wrong signer, wrong audience, expired, replayed and cross-origin proofs all refused; one session per proof | none | none to build; provisioning to run hosted |
| H2 taker identity | Invoice taker is the authenticated payer wallet in hosted mode; the constant stays only in qualification mode; only the taker session can claim or confirm. Gate: cross-wallet and cross-tenant attempts refused, existing digests tests unchanged | H1 | organiser answer on non-enrolled senders |
| H3 hosted journal | Journal logic made storage-independent; D1 adapter with the claim as one batch; authenticated write routes for claim, handoff, confirm and resume; a hosted profile distinct from the loopback demo route. Gate: the same restart, atomicity, unknown-outcome and tamper tests pass on node:sqlite and on local D1 | H2 | owner approval to provision a Cloudflare Worker and D1 (dry run, then production) |
| H4 in-product agreement | Approver and recipient sign the exact terms with eth_signTypedData_v4 from their own wallets; server verifies and stores both. Gate: wrong role, wrong digest, expired and swapped signatures refused | H2 | none |
| H5 real quote and readiness | Server-side firm RFQ bound to the taker by the keyless proof signed in the user's wallet; real balance, allowance and gas checks through qualified RPC. Gate: no quote, over cap and expiry leave no dispatch; live preview and one firm request run under explicit reservation approval | H3, H4, M0 | provider URLs, Textile access, reservation approval |
| H6 dispatch, recovery, receipt | Browser asks the user's wallet to send only the server-claimed envelope; hash or rejection returned; server verifies with two independent providers; resume after a restart shows payout only; receipt shows both references. Gate: real extension read-only checks, then separately approved real sends; routes open only after owner approval | H3 to H5, M2 | owner approval of every financial operation and of the destination |

Targets: H1 and H2 by 29 November, H3 and H4 by 1 December, H5 by 2 December, H6 and the first hosted settlement attempt by 4 December if every external dependency is unblocked. If the hosted path cannot be completed by the review date, the submission must state exactly which path produced each piece of evidence; qualification-mode evidence is never presented as hosted.
