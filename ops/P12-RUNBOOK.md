# P12 operator runbook

## Demonstrations

Use Node 22. Run npm ci in the root, apps/web and workers/api, and install Playwright Chromium. Set DAIDAI_CHROMIUM_PATH if using a separately installed browser.

- **Demo A: local product.** Run `npm run demo:p12 -- product`. Add `--headed` to watch the flow. This recreates only the ignored local D1 fixture, builds the preserved Ink and Brass frontend, reapplies the local schema, and rehearses merchant login, 1,500 cNGN commitment, a scoped payer link, indicative quote, missing authorization, unknown payout, link revocation and cancellation with history. Capture only synthetic amounts, visible states and test totals. Keep invitations, capability fragments and cookies out of recordings.
- **Demo B: public observation.** Run `npm run demo:p12 -- chain`. Show the provider status matrix, Celo chain 42220, registration height, canonical hash, each finalized head and attribution. The fixture hash is the public P08 registration, and the evidence says nothing about invoice settlement. If two independent providers cannot reproduce it, report the partial result and stop the live segment.
- **Preparation contract.** Run `node --experimental-strip-types --test test/p12-settlement.test.ts`. Its firm response, authorization signatures, balances, simulations and receipts are synthetic. Textile's live indicative preview remains optional and separate. [Official RFQ documentation](https://docs.textilecredit.com/api/v2/rfq.html)

## Launch controls and ownership

1. **Hosting.** Configure Vercel to build apps/web on Node 22. Keep both private app access flags off until an environment-specific approval. Cloudflare has the D1 binding placeholder, no public route or Worker preview URL, and a closed runtime mode. The validator is `node scripts/p12-config.mjs`. Only Miniflare exercises the active product in P12. Vercel Hobby is restricted to personal, non-commercial use. A commercial payment service requires an owner-approved compliant hosting arrangement. [Vercel Fair Use](https://vercel.com/docs/limits/fair-use-guidelines)
2. **Identity.** Select the IdP and verify its signature, issuer, audience, expiry and authentication freshness on the server. Wire a tenant membership store, explicit operator role and recent MFA to the new adapter boundary. Bind role assignment and revocation to an audited admin workflow. Invitation login remains for isolated demonstrations. A viewer grant carries no operator or spending authority.
3. **Service credentials.** Add a new independent key ID and secret in the Worker verifier, update the Next server signer, verify the active key, and then remove the old ID after a bounded overlap. Keep credentials in platform secret bindings. During an incident, remove the suspect key immediately, close private entry points, and revoke affected sessions. Global HMAC nonce replay and isolated quotas are stored in D1. Quotas use fixed 60-second windows of 180 signed service requests and 20 invitation exchanges. Boundary bursting and upstream abuse require owner-approved edge limits and monitoring.
4. **D1.** Use a separately approved database for any hosted dry run. Record an encrypted export and a recovery bookmark before any future approved migration. Rehearse additive schemas and restore in disposable storage, compare invoice and attempt counts, and validate immutable commitments and replay constraints. Local schema tests and the walkthrough ran in Miniflare. A remote restore overwrites data, so do not execute or repeat operations after a restore until attempts have been reconciled. [D1 backup and restore](https://developers.cloudflare.com/d1/reference/time-travel/)
5. **Monitoring and rollback.** Assign an incident owner and track signed-request denials, nonce replays, quota exhaustion, D1 failures, missing receipts, conflicting canonical heads and unresolved attempt age. Logs may contain route, outcome and correlation ID. Keep credentials and invoice contents out. On unexpected evidence or data drift, close private gates, preserve lineage records, pin the previous reviewed revision, and independently reconcile before re-enabling access.
6. **Finality proposal.** Use two independently operated providers with successful canonical receipt reads and agreed block/log data. Use the lower independently reported finalized height only after both validate the same canonical block at that height. Check observation freshness and repeat canonical reads. A timeout, reorg, conflicting provider, missing receipt or unavailable finalized block leaves evidence pending or reconciliation required. Provider independence, freshness limits and operator escalation remain owner decisions. [Celo network information](https://docs.celo.org/learn/network/overview)

## First owner-approved settlement

1. Approve a single pilot invoice, verified recipient and consent, exact cNGN target, all-in USDt cap, operator, taker, gas budgets and evidence policy. Confirm the legitimate funding source and approve allowed infrastructure.
2. Verify chain and tokens, gas, balances and existing allowance through reviewed read-only providers. Obtain a fresh firm Textile quote only with separate authority. Bind it to the committed invoice and taker. Check the exact output, included fee, maximum debit, spender, expiry and execution calldata. Keep the claim credential server-only.
3. Review any necessary bounded allowance as its own transaction. Recheck it after finalization, refresh the quote if needed and simulate the exact attributed conversion envelope. Preserve an immutable review and durable unique attempt before any separately approved dispatch.
4. Independently verify successful finalized conversion, including exact cNGN credited to the taker wallet and all-in USDt debited within the cap. With missing or conflicting evidence, preserve the attempt and stop.
5. After conversion verification, prepare a separate exact payout to the committed recipient. Refresh consent, funds, simulation, attribution, operator review and duplicate guards. Seek separate human approval. Declare settlement only after independently verifying the exact finalized payout. An unknown outcome is a reconciliation case and never triggers a retry.
