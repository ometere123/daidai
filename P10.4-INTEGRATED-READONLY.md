## Objective

Deliver a cohesive, demonstrable, **non-spending** application architecture:
- a read-only backend API for Cloudflare Workers with D1 persistence, prototyped locally;
- a typed server-side integration from the Next.js app on Vercel;
- an internal authoritative invoice demonstration;
- GitHub Actions CI.

It does not include production deployment, real funds, wallet execution, or a public private-invoice route.

## Architecture

```
Browser ──▶ Next.js on Vercel (server components / route handlers only)
              │  fixture demo (unchanged, demo-only)
              │  internal authoritative demo: off unless DAIDAI_INTERNAL_DEMO=1 and not VERCEL_ENV=production
              │  server-only API client: signs each request (HMAC service key), forwards the viewer session token
              ▼
          Cloudflare Worker (workers/api), read-only
              1. service authentication (HMAC over method, path, timestamp, nonce, body digest; ±60 s; nonce replay window)
              2. request validation (versioned contract, src/api-contract.ts)
              3. viewer authentication (session-token hash lookup) → AuthenticatedViewer (P10.3 brand)
              4. invoice-scoped permission + tenant directory (P10.3 invoiceViewerAuthorizer) BEFORE any invoice read
              5. P10.3 projector over D1 repositories + read-only evidence adapters
              6. response contract (schema v2 projection | uniform error), Cache-Control: no-store, no CORS
          Cloudflare D1 (local prototype only)
              invoices, signatures, sessions, permissions, tenant directory, attempt lineage (same invariants as node:sqlite)
```

### Trust boundaries

| Boundary | Trusted side | Mechanism | Never trusted |
| --- | --- | --- | --- |
| Browser → Vercel | Vercel server | Server-side rendering only. The browser never receives backend credentials. The internal demo is gated by an environment flag and disabled in production | Client-supplied viewer IDs, grants or tenant IDs |
| Vercel → Worker | Worker | HMAC service authentication with a key held as a Worker secret and a Vercel server environment variable (never `NEXT_PUBLIC_*`) | `Origin`-bearing browser requests (rejected), unsigned or replayed requests |
| Worker → viewer | Worker | Session-token hash lookup in D1 with expiry. The session must be issued server-side (no login flow yet) | Wallet connections, invoice approval or consent signatures as identity |
| Worker → data | Projector | P10.3 attested adapters. D1 repositories attest only after re-deriving commitments and validating rows | Source labels, caller-named verifiers |
| Worker → chain | Projector | P10.3 `readOnlyRpc` (four read methods). **No chain reader is configured by default**, so operations stay `unknown/unavailable` | Fixture chain data as authoritative evidence |

### Failure modes and required behaviour

| Failure | Required behaviour |
| --- | --- |
| Missing, invalid, stale or replayed service signature | 401 with a uniform body. No data access |
| Missing or expired viewer session, no permission, or cross-tenant request | A uniform `not-found-or-forbidden`, indistinguishable from a missing invoice. No invoice read |
| Malformed request (ID, version, extra fields) | 400 `invalid-request` before authentication work that touches data |
| D1 unavailable, or a corrupted or tampered row | Fail closed: null projection, or `reconciliation-required` |
| No chain reader, or chain unavailable | Operation `unknown/unavailable`; never settled |
| Duplicate, unknown or hashless attempt; new digest after a final payout | Blocked by both the node and D1 lineage schemas |
| `verified-final` from a caller-supplied verifier name | Refused. Only attested, finalized evidence can record `verified-final` |
| Caching of private responses | `Cache-Control: no-store, private` on the Worker and dynamic, non-cached rendering on Vercel |
| Logs | No tokens, signatures, keys or raw request bodies are logged |

## What was built

### Backend (Cloudflare Worker, `workers/api`)
- **Read-only HTTP pipeline (`src/handler.ts`):**
  1. A request with an `Origin` header gets a uniform 401, and no CORS headers are ever sent.
  2. Non-GET requests get 405.
  3. Contract parse failures get 400.
  4. HMAC service authentication applies to every route, health included: key id, ±60 s, nonce window, constant-time compare.
  5. A per-isolate token bucket per key gives 429. It runs only after authentication.
  6. Then the viewer session lookup (SHA-256 of the token), the tenant directory and the explicit `invoice:read` permission, then the P10.3 projector.
  7. Every denial gets the same 404 body, and exceptions get 503 with no detail.
  8. Responses are re-validated with `parseResponse`, sent `no-store`, and logged with only the request id, route, status and key id.
- **D1 repositories:** SELECT-only, with attempt rows attested in the same way as the node reader. A test asserts that every read-path query is a SELECT.
- **D1 lineage writer:** a prototype for tests, never imported by the Worker. It mirrors the node store using atomic `batch()` and conditional writes. The shared triggers enforce the invariants.
- **No chain reader is configured.** Conversion and payout therefore stay `unknown/unavailable`, and nothing can settle. The Worker has no code path that configures a chain from request input.

### Shared core (`src/`)
- **Worker-safe modules:** `invoice-core.ts` and `chain-evidence.ts`, re-exported by `invoice.ts` and `evidence-adapters.ts`.
- **`lineage-schema.ts`:** a single statement list used by both node:sqlite and D1.
- **`api-contract.ts`:** versioned and runtime-validated, with strict exact-key response validation.
- **`service-auth.ts`:** HMAC signing using WebCrypto.
- **`repositories.ts`:** the repository interfaces and their composition into attested projection sources.
- **Lineage policy:**
  - **Per invoice operation (A7):** an open or `verified-final` attempt under any commitment blocks the same operation for the invoice.
  - **Evidence-only `verified-final` (C3):** it can only come from attested evidence bound to the attempt, its revision, commitment and operation, and must be canonical and finalized, through `recordVerifiedFinal`. `appendVerification` refuses it, and the closure trigger also requires the `attested-evidence` marker.

### Frontend (`apps/web`, stays on Vercel)
- **`lib/daidai-api.ts`:**
  - It is server-only and throws in a browser context.
  - It reads `DAIDAI_API_BASE_URL`, `DAIDAI_SERVICE_KEY_ID` and `DAIDAI_SERVICE_KEY` from the environment, never `NEXT_PUBLIC_*`.
  - It signs each request, uses `cache: 'no-store'`, `redirect: 'error'` and a 5 s timeout, validates every response, and logs nothing.
- **`lib/internal-demo.ts`:** a gate evaluated at request time. It is on only when `DAIDAI_INTERNAL_DEMO` is exactly `1`, and always off when `VERCEL_ENV=production`.
- **`/internal/authoritative/[invoiceId]`:**
  - When the gate is off, it returns 404.
  - When on, it renders as `force-dynamic` and noindex, with an "Authoritative · Internal read-only demonstration" banner, a no-chain-reader notice and the internal `AuthoritativeInvoiceView`.
  - Every failure shows the same message.
- **Fixture demo:** unchanged and still visibly "Demo".
- **`next.config.mjs`:** the Turbopack root is the repo root, so server code can import the shared contract. The root `npm ci` is required, and on Vercel "include files outside the root directory" must be enabled.

### CI (`.github/workflows/ci.yml`)

- **Safety settings:** `contents: read` permissions, actions pinned to commit SHAs, `persist-credentials: false`, and no secrets, wallets, RPC credentials or deploys.

## Vercel ↔ Cloudflare integration path (not deployed)

1. **Worker:** `wrangler secret put DAIDAI_SERVICE_KEYS` (JSON `{keyId: secret}`, at least 32 random characters per secret), and provision a D1 database and set its real `database_id`. Both require the owner's approval: no paid changes, no deployment in this milestone.
2. **Vercel:** set the server environment variables `DAIDAI_API_BASE_URL`, `DAIDAI_SERVICE_KEY_ID` and `DAIDAI_SERVICE_KEY`. **Never set** `DAIDAI_INTERNAL_DEMO_ALLOW_PROD_BUILD`, and leave the demo gate off in production.
3. **Key rotation:** add a new key id to the Worker, switch Vercel over, then remove the old key.
4. **Before production:** real session issuance and revocation (a login flow), a global nonce store (Durable Object or D1), a reviewed read-only chain reader, and a read-only D1 access pattern. D1 bindings can write, so read-only is enforced by code and review only.

## Adversarial review (independent agent)

- **New suites:** `test/p104-adversarial.test.ts` (10 tests) and `workers/api/test/adversarial.test.ts` (40 tests).
- **What they attacked:**
  - signature canonicalization and percent-encoding variants;
  - header injection and duplication;
  - prototype-named key ids, timestamp formats, replay, and the rate limiter;
  - browser headers, and byte-identical uniform denials;
  - session and permission boundaries, SQL injection, and the read-path SELECT-only property;
  - tampered rows, forged attempts and signatures, and D1 writer races;
  - node and D1 parity across an 18-step adversarial sequence;
  - the lineage policy, the web client's URL, redirect and response handling, and the demo gate truth table.
- **Finding (nonblocking, fixed):** an attempt already closed `verified-final` could be closed again, appending a duplicate `closed` event under a different operator name. This happened in both node and D1, because the close-once trigger only fired when the value changed. It is fixed by a new `attempt_closed_terminal` trigger, which refuses any update once closed and also covers raw SQL and existing databases, plus a `closed IS NULL` check in both writers. It is kept as `FIXED (P10.4 adversarial finding)` tests.
- **Hardened from observations:** the demo gate now treats `VERCEL_ENV` case- and whitespace-insensitively.
- **Observations kept as documented behaviour:**
  - `NonceWindow` evicts entries beyond 50k per isolate. This adds to the documented need for a global nonce store.
  - If an invoice is re-committed to a new digest, the projection doesn't show earlier-digest attempts. The schema still refuses a new attempt, so no double payment is possible. Showing them is a nonblocking improvement.
  - The web client relies on the validated error body rather than the HTTP status.
  - A raw SQL writer can forge an `attested-evidence` verdict. That can only *block* further attempts, never settle, and raw writers are inside the trust boundary.

## Remaining items

**1. Blocking security defects:** none open in the read-only scope.

**2. Nonblocking improvements:**
- show earlier-digest attempts in the projection;
- treat the HTTP status as a second signal in the web client;
- reject `Sec-Fetch-*` headers too;
- move the projection types to a dependency-free module, so the web app doesn't load the Celo attribution package;
- bump `actions/checkout` and `actions/setup-node` to versions that run on Node 24 (GitHub warns about Node 20).

**3. External dependencies:**
- a real identity provider and session issuance;
- a provisioned D1 database and Worker secrets;
- a reviewed read-only Celo chain reader and endpoint;
- a global nonce store (Durable Object or D1);
- Vercel's "include files outside root directory" setting.

**4. Decisions for the product owner:**
- the finality policy (how many confirmations count as final);
- the authoritative reconciliation design, which is needed before any second attempt;
- whether an amended commitment may ever be paid (it is currently blocked per invoice operation);
- approval for D1 provisioning and Worker deployment;
- the Vercel Hobby non-commercial constraint for any payment-adjacent use.

## Before real Textile FX conversion and cNGN payout

None of this exists yet. Each item needs separate review and human authorization:
1. **Viewer and operator authentication:** a real login and sessions, and operator authorization for execution.
2. **Lineage at claim time:** the execution service must write lineage when it claims an attempt (`recordAttempt` before dispatch, then `recordHash`).
3. **Persistence:** a durable, reviewed store for invoices, signatures and lineage. Production D1 needs a read-only access pattern and global replay protection.
4. **A production read-only chain reader** with a finality policy, wired through `chain-evidence.ts`. `recordVerifiedFinal` is driven only by its attested output.
5. **Authoritative reconciliation (proof of non-execution)** before any new attempt can be allowed.
6. **Per-transaction human approval in MetaMask,** with preflight checks: balances, allowance ceilings and fee ceilings (`CeloReader.preflight`).
7. **Textile:** RFQ and taker-proof flows reviewed against live terms, and the exact-output quote revalidated at signing.
8. **Funding:** USDt for conversion and CELO for gas, with an explicit owner decision on limits.
